# Refactor Plan: Agent Architecture with Persistent Sessions

## Overview

Multi-agent system with **disk-persisted sessions**, organized in 3 context layers (human → project → session), where internal agent communication is exclusively in **English**, and human communication happens in their **language/slang** through an intermediary agent (Delivery).

The Delivery filters translation: the human can watch what's happening in real-time, but by default the Delivery only shows a **summary for context** + a **general plan**. If the human wants, the thinking is not translated, only the plan is shown.

---

## 1. Folder Structure

```
~/.config/opencode/                          # Global IDE config (e.g., C:\Users\Admin\.config\opencode\)
└── sessions/
    └── {humano}/                            # Human name (OS username, e.g., "admin")
        ├── humano.md                        # Human profile (name + vocabulary/slang)
        └── {proyecto}/                      # Project name (e.g., "goland-api")
            ├── project.md                   # Synced copy + strict project slang
            └── {sesion}/                    # Work session (DDMMYYYY-keywords)
```

## 2. Context Files Definition

### 2.1 `humano.md` (Level: Human)

**Location:** `~/.config/opencode/sessions/{humano}/humano.md`

**Purpose:** Human profile. Contains their name and a dictionary of personal vocabulary/slang. The Delivery updates it incrementally as it detects new terms.

**Construction Rules:**
- The dictionary must be **compact**: if it grows too large, it increases processing cost
- The Delivery decides when to add a new term (only if recurrent or ambiguous)
- If the dictionary exceeds a certain size, the Delivery must alert the human
- The human can edit it at any time

**Structure:**
```markdown
# Human Profile

## Identity
- **Name**: Admin
- **OS Username**: admin
- **Language**: Spanish (Argentine)
- **Preferred address**: Vos

## Session Naming Rules
- Format: `DDMMYYYY-keywords`
- Date is mandatory
- Keywords: 2-4 words, kebab-case, derived from the prompt topic
- Human must confirm or rename the proposed session name

## Vocabulary / Lunfardo
| Term | Meaning | Context |
|------|---------|---------|
| "laburo" | work/job | General use |
| "quilombo" | mess/chaos | When things are complex |
| "che" | hey/look | Attention getter |
| "posta" | seriously/for real | Emphasis |
| ... | ... | ... |

## Communication Preferences
- **Thinking visibility**: Summary only (default) | Full thinking (optional)
- [Any other preferences the human has expressed]
```

### 2.2 `project.md` (Level: Project)

**Location:** `~/.config/opencode/sessions/{humano}/{proyecto}/project.md`

**Purpose:** Synced copy of the repo's `project.md`, enriched with **strict project slang** (internal names, conventions, acronyms).

**Construction Rules:**
- Copied from `.opencode/project.md` in the repo
- If created from scratch, the Delivery asks the user for examples
- Synced when the repo changes (Delivery detects and updates)
- Project slang is **separate** from human slang
- **Project slang is inferred, not asked**: The Delivery observes the codebase and infers internal terminology. For example, in this project "polvo" (dust) refers to the special powder inside fire extinguishers. The Delivery detects these domain-specific meanings from context, code comments, and usage patterns.

**Structure:**
```markdown

## Basic Info
- **Project**: goland-api
- **Language**: Go 1.21
- **Framework**: Gin
- **Database**: PostgreSQL 15
- **ORM**: GORM
- **Testing**: testify
- **Frontend**: None (API only)

## Architecture
- **Pattern**: Onion/Clean Architecture
- **Structure**:
  - `internal/domain/` - Domain models and interfaces
  - `internal/repository/` - Data access layer
  - `internal/service/` - Business logic
  - `internal/transport/http/` - HTTP handlers and routing

## Commands
- Run: `go run cmd/server/main.go`
- Test: `go test ./...`
- DB: `docker compose up -d db`

## Project Vocabulary / Lunfardo (Inferred)
| Term | Meaning | Where Used | Confidence |
|------|---------|------------|------------|
| "polvo" | Fire extinguisher powder | internal/domain/permissions | High |
| "matafuegos" | Fire extinguisher | Config files | High |
| "feature flag" | Permission bitmask | internal/domain/permissions | High |
| ... | ... | ... | ... |

## Key Conventions
- [Naming conventions]
- [Error handling patterns]
- [API response format]
```

### 2.3 `general-context.md` (Level: Session)

**Location:** `~/.config/opencode/sessions/{humano}/{proyecto}/{sesion}/general-context.md`

**Purpose:** Entry point for each session. Contains the original prompt, its classification, and all attachments with their descriptions.

**Attachment Rules:**
- If the IDE provides the image, it's saved in `assets/` and referenced here
- If the agent cannot access the image, it saves only the textual description
- Each attachment has: name, size, description, observations
- If an attachment is too heavy to load in memory, only the description is used
- **Image coordination**: The agent must comment on what it's keeping from the image, to coordinate with the human what's important. If it's text, transcribe it. If it's a frontend overlap, try to open the image only once to confirm what the user proposes to see.

**Structure:**
```markdown
# Session Context

## Original Prompt
> [Exact prompt as received from the human, in their language]

## Prompt Classification
- **Type**: [bug | task | feature-design | update]
- **Confidence**: [high | medium | low]

[Translation and enhancement of the prompt, in English, for internal agent use]

## User Hints / Clues
- [Any hints the user provided]
- [Any constraints mentioned]

## Attachments
| # | File | Size | Type | Description | Notes |
|---|------|------|------|-------------|-------|
| 1 | assets/diagram.png | 245KB | Image | Architecture diagram showing agent flow | Hand-drawn, some text is hard to read |
| 2 | assets/error-log.txt | 12KB | Text | Stack trace from production | Contains PII, redacted |

## Attachment Processing Log
### 1. diagram.png
- **Action taken**: Opened once to confirm content with user
- **What was kept**: Text description of the 4-layer agent flow
- **What was discarded**: Visual layout (not relevant for text-based processing)
- **User confirmation**: User confirmed the description is accurate
- **Memory cost**: High (image) → Using text description for agent context

### 2. error-log.txt
- **Action taken**: Full transcription
- **Content**: [Transcribed text here]
- **Memory cost**: Low (text) → Full content available for agents
```

## 3. Agent Definitions

### 3.1 DELIVERY AGENT

**Role:** Interface between the human and the agent system. The only agent that speaks with the human.

**Responsibilities:**
1. Receive the human's prompt (in their language/slang)
2. Create the session structure (folders + files)
3. Propose session name → human confirms or renames
4. Load `humano.md` (human's slang)
5. Load/sync `project.md` (project's slang)
6. Create `general-context.md` with original prompt, classification, and attachments
7. Translate EVERYTHING to English before passing to Orchestrator
8. Receive agent responses (in English) and **filter/summarize** for the human
9. Update `humano.md` with new vocabulary it detects (if compact)
10. Alert if `humano.md` dictionary grows too large
11. **Coordinate image processing**: Comment on what's being kept from images, coordinate with human what's important

**Tools:** write, edit, bash, read, skill, task

**Translation Filtering Rules:**
- The human can watch what's happening in real-time
- By default, the Delivery only shows a **summary for context** + a **general plan**
- The thinking process is NOT translated by default
- If the human explicitly requests it, the Delivery can show the full thinking
- The Delivery must always be ready to provide more detail if asked

**Communication Flow:**
```
Human → Delivery: Spanish/slang (full content)
Delivery → Orchestrator: English (full content)
Orchestrator → Delivery: English (full content)
Delivery → Human: Spanish/slang (filtered: summary + plan only)
```

**Rules:**
- NEVER speaks English with the human
- NEVER passes Spanish to the Orchestrator
- Always loads `humano.md` before communicating with the human
- Always loads `project.md` before creating session context
- If it cannot fulfill an attachment rule, it alerts to improve it
- When processing images, coordinates with the human what's important

### 3.2 ORCHESTRATOR AGENT

**Role:** Reviews the session folder, releases subagents, and coordinates responses in the same folder.

**Responsibilities:**
1. Read `general-context.md` from the active session
2. Read `enhanced-prompt.md` if it exists (from Prompt Enhancer)
3. Read `scope.md` if it exists (from Context Reducer)
4. Decide which subagents to release based on session state
5. Pass context in English to subagents
6. Receive subagent responses (in English) and save them in the session folder

**Tools:** write, edit, bash, read, task

**Rules:**
- Only works in English
- Only reads/writes in the active session folder
- Does not communicate directly with the human
- If it needs information from the human, it asks the Delivery

**Decision Flow:**
```
1. Does general-context.md exist? → If no, wait for Delivery
2. Does enhanced-prompt.md exist? → If no, release Prompt Enhancer
3. Does scope.md exist? → If no, release Context Reducer
4. Is scope defined? → Release resolution agents (coder, tester, etc.)
```

### 3.3 PROMPT ENHANCER (Subagent)

**Role:** Enhances the original prompt, structures it, identifies affected modules.

**Responsibilities:**
1. Read `general-context.md`
2. Read `project.md` (slang + project stack)
3. Classify the prompt (bug/task/feature-design/update)
4. Structure: problem, user hints, conditions, affected modules
5. Generate `enhanced-prompt.md` in the session folder

**Tools:** write, edit, bash, read

**Output (`enhanced-prompt.md`):**
```markdown
# Enhanced Prompt

## Classification
- **Type**: [bug | task | feature-design | update]

## Problem Statement
[Clear, structured description in English]

## User Hints / Clues
- [What the user mentioned]

## Conditions / Constraints
- [Technical constraints]
- [Business constraints]

## Affected Modules
| Module | Why |
|--------|-----|
| [Module] | [Reason] |

## Acceptance Criteria
- [ ] Criterion 1
- [ ] Criterion 2

## Edge Cases
- [Edge case 1]
- [Edge case 2]
```

### 3.4 CONTEXT REDUCER (Subagent)

**Role:** Analyzes the enhanced prompt and defines minimum and maximum scope, detects hotspots, generates theories.

**Responsibilities:**
1. Read `enhanced-prompt.md`
2. Read `project.md`
3. Explore the codebase to identify relevant modules
4. Detect hotspots (critical code, complex dependencies)
5. Define minimum and maximum scope
6. Generate theories about the solution
7. Save `scope.md` in the session folder

**Tools:** bash, read (NO write/edit — analysis only)

**Output (`scope.md`):**
```markdown
# Scope Definition

## Problem Summary
[Brief summary]

## Hotspots Detected
| Area | Risk | Why |
|------|------|-----|
| [Area] | [High/Med/Low] | [Reason] |

## Minimum Scope
[What MUST be done]

## Maximum Scope
[What COULD be done if time allows]

## Theories
1. [Theory 1 about the solution approach]
2. [Theory 2]

## In-Scope Modules
| Module | Files | Action |
|--------|-------|--------|
| [Module] | [files] | [read/modify/create] |

## Out-of-Scope
| Module | Why |
|--------|-----|
| [Module] | [Reason] |

## Dependencies
- **Upstream**: [What this depends on]
- **Downstream**: [What depends on this]

## Risks
- [Risk 1]
- [Risk 2]
```

## 4. Communication Rules

| Interaction | Language | Rule |
|-------------|----------|------|
| Human → Delivery | Spanish/slang | Human speaks as they want |
| Delivery → Human | Spanish/slang | Uses `humano.md` as reference |
| Delivery → Orchestrator | English | Full translation |
| Orchestrator → Subagents | English | All context in English |
| Subagents → Orchestrator | English | Outputs in English |
| Orchestrator → Delivery | English | Results in English |
| Delivery → Human (filtered) | Spanish/slang | **Summary + plan only** (default) |

### 4.1 Translation Filtering (Key Rule)

**Default Behavior:**
- The human can watch what's happening in real-time (optional)
- The Delivery only shows a **summary for context** + a **general plan**
- The thinking process is NOT translated

**Optional Behavior:**
- If the human explicitly requests it, the Delivery can show the full thinking
- The human can change this preference at any time
- The preference is stored in `humano.md` under "Communication Preferences"

**Example:**
```
[Internal: Orchestrator → Delivery in English]
"Prompt Enhancer has classified this as a bug. The login module has a race condition 
in the token refresh logic. The fix requires modifying internal/service/auth_service.go 
lines 142-158. The Context Reducer identified 3 hotspots..."

[Filtered: Delivery → Human in Spanish/slang]
"Che, ya clasifiqué el problema: es un bug en el login. Hay una condición de carrera 
al refrescar el token. El plan es modificar el auth_service para arreglarlo. 
Después te paso los detalles si querés."
```

## 5. Attachment Rules

### 5.1 General Rules

1. **If the IDE provides the file:** Save in `assets/` and reference in `general-context.md`
2. **If the agent cannot access the file:** Save only the textual description
3. **Each attachment must have:**
   - File name
   - Size
   - Description of what it shows
   - Relevant observations
4. **Memory cost:** If an attachment is too heavy (large image), use only the textual description for agent context
5. **If an agent cannot fulfill the rule:** It must alert the Delivery to improve it

### 5.2 Image Processing Rules

**Coordination with Human:**
- The agent must comment on what it's keeping from the image
- Coordinate with the human what's important to extract
- The human has the final say on what's relevant

**Processing by Type:**

**If it's text (screenshot of code, error message, etc.):**
- Transcribe the full text
- Save transcription in `general-context.md`
- Keep the image reference for future use if needed

**If it's a frontend overlap (UI screenshot, design mockup, etc.):**
- Try to open the image **only once** to confirm what the user proposes to see
- Ask the user: "I see [X] in the image. Is that what you want me to focus on, or is there something else?"
- After confirmation, extract only what's relevant
- Save the extraction in `general-context.md`

**If it's a diagram or architecture:**
- Open once to understand the structure
- Describe the key elements in text
- Ask the user if the description is accurate
- Save the text description for agent use

**Example Log:**
```markdown
## Attachment Processing Log
### 1. frontend-bug.png
- **Type**: Frontend overlap (UI screenshot)
- **Action taken**: Opened once to confirm content with user
- **What I see**: Login form with email field showing red error border
- **User confirmation**: User confirmed this is the issue
- **What was kept**: Description of the error state and field validation
- **What was discarded**: Visual styling details (not relevant for backend fix)
- **Memory cost**: High (image) → Using text description for agent context
```

## 6. Slang Rules

### 6.1 Human Slang (`humano.md`)

**Construction:**
- Incremental: The Delivery adds terms as it detects them
- Compact: If the dictionary grows too large, the Delivery alerts
- Only useful terms: Don't save obvious or one-time-use terms
- The human can edit it at any time

**Detection Rules:**
- Only add terms that are recurrent or ambiguous
- If a term is used once and never again, don't add it
- If a term has multiple meanings, add it with context

### 6.2 Project Slang (`project.md`)

**Construction:**
- **Inferred, not asked**: The Delivery observes the codebase and infers internal terminology
- The Delivery detects domain-specific meanings from:
  - Code comments
  - Variable names
  - Function names
  - Documentation
  - Usage patterns
- Example: In this project, "polvo" (dust) refers to the special powder inside fire extinguishers. The Delivery detects this from context.

**Confidence Levels:**
- **High**: Term is used consistently with the same meaning across multiple files
- **Medium**: Term is used in a few places with consistent meaning
- **Low**: Term is used once or has ambiguous meaning

**Sync Rules:**
- First time: If it doesn't exist, the Delivery asks the user for examples to create it
- Sync: The Delivery detects changes in `.opencode/project.md` in the repo and updates the copy
- Conflicts: If the repo changes and the local copy has additional slang, merge (don't overwrite)

## 10. Migration Strategy

### Current State
- SDD Agent exists and works
- canonical-prompter skill exists
- context-reductor skill exists
- Subagents exist (coder, tester, reviewer, etc.)

### Migration Steps
1. **Keep existing agents**: Don't break what works
2. **Add new agents**: Delivery, Orchestrator, Prompt Enhancer, Context Reducer
3. **Deprecate SDD Agent**: Gradually replace with Delivery + Orchestrator
4. **Migrate skills**: canonical-prompter → Prompt Enhancer, context-reductor → Context Reducer
5. **Test in parallel**: Run both systems in parallel for a week
6. **Full cutover**: Switch completely to the new architecture

---

## 11. Success Criteria

1. **Session persistence**: All sessions are saved in `~/.config/opencode/sessions/`
2. **Language separation**: Internal communication is in English, human communication is in their language
3. **Translation filtering**: Human only sees summary + plan by default
4. **Attachment coordination**: Images are processed with human coordination
5. **Slang inference**: Project slang is inferred from codebase, not asked
6. **Compact dictionaries**: `humano.md` stays compact and useful
7. **Agent coordination**: Orchestrator correctly releases agents based on session state
8. **No breaking changes**: Existing workflows continue to work during migration

---

## 12. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Dictionary grows too large | High processing cost | Delivery alerts human, prunes dictionary |
| Image processing fails | Cannot extract context | Fallback to text description only |
| Agent miscommunication | Wrong outputs | All agents work in English, clear protocols |
| Session folder bloat | Disk space issues | Implement cleanup policy for old sessions |
| Slang inference errors | Wrong context | Confidence levels, human can correct |
| Translation filtering too aggressive | Human misses important info | Human can request full thinking at any time |
